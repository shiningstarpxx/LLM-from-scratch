### Q10: 什么是Bank Conflict？

**引导思考**:
- Shared Memory虽快，但有陷阱
- 多个线程同时访问，如何避免冲突？
- 什么是Bank？

**Bank结构**:
```
Shared Memory被分成32个Bank
每个Bank可以独立访问

理想情况:
32个线程访问32个不同Bank → 完美并行

Bank Conflict:
多个线程访问同一Bank → 串行化！
性能下降32倍！⚠️
```

**如何避免**:
```c
// Bad: Bank Conflict
__shared__ float data[1024];
float x = data[threadIdx.x * 2];  // 只用了16个banks

// Good: No Conflict  
float x = data[threadIdx.x];  // 用满32个banks
```

### Q12: 为什么Register是最快的？

**引导思考**:
- Register File直接在SM核心旁边
- 每个线程有自己的寄存器
- 但是有限制...

**Register特点**:
```
速度: ~1 cycle延迟（最快！）
容量: 每个线程~255个寄存器
总量: ~65K个寄存器/SM

权衡:
使用更多寄存器 → 能跑的线程更少
→ Occupancy降低
→ 延迟隐藏能力下降

优化目标: 平衡寄存器使用和Occupancy
```

**Occupancy计算**:
```python
def calculate_occupancy(
    registers_per_thread: int,
    shared_mem_per_block: int,
    threads_per_block: int
) -> float:
    # 寄存器限制
    max_blocks_regs = 65536 // (registers_per_thread * threads_per_block)
    
    # Shared Memory限制
    max_blocks_smem = 164*1024 // shared_mem_per_block
    
    # 实际能跑的blocks
    actual_blocks = min(max_blocks_regs, max_blocks_smem, 16)
    
    # Occupancy = 实际warps / 理论最大warps
    actual_warps = actual_blocks * (threads_per_block // 32)
    max_warps = 64  # A100的最大warps/SM
    
    return actual_warps / max_warps
```

## Part 3: 计算与带宽 (Q13-Q18)

### Q13: 什么是Arithmetic Intensity？

**引导思考**:
- 一个kernel执行了很多FLOP
- 但也读写了很多字节
- 如何衡量计算密集度？

**定义**:
```
Arithmetic Intensity (AI) = FLOP / Bytes

单位: FLOP/Byte

高AI: 计算密集，适合GPU
低AI: 内存密集，可能瓶颈
```

**例子分析**:
```python
# 矩阵乘法 C = A @ B
# A: [M, K], B: [K, N], C: [M, N]

FLOP = 2 * M * K * N  # 每个元素需要K次乘加

Bytes = (M*K + K*N + M*N) * 4  # FP32, 读A, B, 写C

AI = (2*M*K*N) / ((M*K + K*N + M*N) * 4)

如果M=N=K=1024:
AI = 2*1024³ / (3*1024²*4) 
   = 2*1024 / (3*4)
   = 170 FLOP/Byte  # 很高！✅

如果M=N=K=32:
AI = 2*32³ / (3*32²*4)
   = 64 / 12
   = 5.3 FLOP/Byte  # 偏低 ⚠️
```

**连接Lecture 03**:
```python
# Attention: Q @ K.T
# Q, K: [batch, heads, seq, d_k]

FLOP = 2 * batch * heads * seq² * d_k
Bytes = 2 * batch * heads * seq * d_k * 4  # 读Q, K

AI = (2*seq² *d_k) / (2*seq*d_k*4)
   = seq / 4

seq=1024: AI = 256 FLOP/Byte ✅ (高)
seq=128:  AI = 32 FLOP/Byte  ⚠️ (中)
seq=32:   AI = 8 FLOP/Byte   ❌ (低)

短序列的attention是memory-bound!
```

### Q16: 为什么FlashAttention能加速？(硬件视角)

**引导思考**:
- Lecture 03学了FlashAttention算法
- 现在从硬件角度理解
- 核心是什么？

**标准Attention的问题**:
```python
# 标准实现
S = Q @ K.T / sqrt(d_k)       # [batch, heads, seq, seq]
P = softmax(S, dim=-1)        # 写HBM ⚠️
O = P @ V                     # 读HBM ⚠️

HBM访问:
- 写S矩阵: batch * heads * seq² * 4 bytes
- 写P矩阵: batch * heads * seq² * 4 bytes
- 读P矩阵: batch * heads * seq² * 4 bytes

对于seq=1024, heads=8:
= 3 * 8 * 1024² * 4
= 96 MB per batch

主要瓶颈: HBM带宽！⚠️⚠️
```

**FlashAttention的解决方案**:
```python
# Tiling策略
for tile_q in tiles(Q):              # TILE_SIZE × d_k
    load tile_q to SRAM               # 64KB
    
    for tile_k, tile_v in tiles(K, V):
        load tile_k, tile_v to SRAM   # 128KB
        
        # 全部计算在SRAM中进行！
        tile_s = tile_q @ tile_k.T / sqrt(d_k)
        tile_p = softmax(tile_s)      # 在SRAM ✅
        tile_o = tile_p @ tile_v      # 在SRAM ✅
        
        # 只写最终结果到HBM
        accumulate tile_o to global_o

HBM访问:
- 读Q, K, V: 2 * batch * seq * d_model * 4
- 写O: batch * seq * d_model * 4

减少了seq倍的访问！
seq=1024: 减少1000倍HBM访问！✅✅✅
```

**硬件视角的加速原因**:
```
1. 数据复用 (Data Reuse)
   - Q的每个tile被K的多个tile复用
   - 减少HBM读取

2. SRAM计算 (On-Chip Compute)
   - Softmax在SRAM中完成
   - SRAM速度是HBM的100倍！

3. Arithmetic Intensity提升
   - 标准: AI ~ 50 FLOP/Byte
   - Flash: AI ~ 5000 FLOP/Byte ✅
   - 从memory-bound → compute-bound

4. 带宽利用率优化
   - 连续访问，coalesced
   - 减少内存事务数
```

**实际加速比**:
```
理论分析:
HBM带宽节省: ~1024倍 (seq维度)
实际加速: 2-4倍

为什么不是1024倍?
1. 计算时间不是0
2. SRAM容量限制 (需要多次循环)
3. Recomputation开销 (反向传播)
4. Kernel launch开销

但2-4倍已经是巨大的提升！✅
```

### Q17: Tiling的本质是什么？

**引导思考**:
- Tiling不只是FlashAttention用
- 这是通用的优化技术
- 本质是什么？

**Tiling的核心思想**:
```
不是:
一次处理全部数据

而是:
分块处理，最大化数据复用

目标:
让数据尽可能留在快速内存(SRAM)中
```

**数学建模**:
```python
# 矩阵乘法 C = A @ B
# A: [M, K], B: [K, N]

# Naive (没有tiling)
for i in range(M):
    for j in range(N):
        for k in range(K):
            C[i,j] += A[i,k] * B[k,j]

# 内存访问: M*N*K 次读A, M*N*K 次读B
# 极其低效！每个元素读K次！

# Tiling
TILE_SIZE = 32
for i0 in range(0, M, TILE_SIZE):
    for j0 in range(0, N, TILE_SIZE):
        for k0 in range(0, K, TILE_SIZE):
            # 加载tiles到Shared Memory
            tile_A = A[i0:i0+TILE, k0:k0+TILE]
            tile_B = B[k0:k0+TILE, j0:j0+TILE]
            
            # 在Shared Memory中计算
            compute_tile(tile_A, tile_B)

# 内存访问: M*K + K*N (只读一次！)
# 数据复用: TILE_SIZE倍！
```

**Tiling参数选择**:
```
Tile Size选择:
- 太小: 循环开销大
- 太大: 超出Shared Memory

最优: 刚好填满Shared Memory
A100: 164KB/SM

矩阵乘法:
TILE_SIZE² * 4 bytes * 2 (A+B) < 164KB
TILE_SIZE < sqrt(164*1024/8) = 143
→ 通常选128
```

**通用Tiling模式**:
```python
class TiledComputation:
    def __init__(self, data_size, tile_size, sram_size):
        self.data_size = data_size
        self.tile_size = tile_size
        self.sram_size = sram_size
        
    def memory_traffic(self):
        # 无tiling
        naive = self.data_size * self.num_accesses
        
        # 有tiling
        num_tiles = math.ceil(self.data_size / self.tile_size)
        tiled = self.data_size + num_tiles * self.tile_size
        
        # 加速比
        speedup = naive / tiled
        return speedup
    
    def compute_optimal_tile_size(self):
        # 最大化数据复用
        # 约束: tile_size * data_per_element < sram_size
        optimal = math.sqrt(self.sram_size / self.data_per_element)
        return optimal
```

### Q18: Fusion为什么重要？

**引导思考**:
- 多个操作分别执行 vs 融合执行
- 哪个更快？为什么？
- Fusion的本质？

**Kernel Fusion的概念**:
```python
# 不融合
def unfused(x):
    y = relu(x)       # Kernel 1: 读x, 写y到HBM
    z = layer_norm(y) # Kernel 2: 读y, 写z到HBM
    return z

# HBM访问: 读x + 写y + 读y + 写z = 4次

# 融合
def fused(x):
    # 单个kernel
    y = relu(x)        # 在寄存器/SRAM
    z = layer_norm(y)  # 在寄存器/SRAM
    return z

# HBM访问: 读x + 写z = 2次
# 节省50%带宽！✅
```

**Fusion的收益**:
```
1. 减少HBM访问
   - 中间结果留在快速内存
   - 带宽节省 ~ (n-1)/n for n操作

2. 减少kernel launch开销
   - 每个kernel有~10μs开销
   - 融合减少launch次数

3. 提高Arithmetic Intensity
   - 更多计算相对于内存访问
   - 从memory-bound → compute-bound

4. 减少内存占用
   - 不需要存储中间结果
   - 重要for大模型！
```

**实际例子: Transformer Block**:
```python
# Transformer的计算流
# 不融合: 6个独立kernels
x = input
x = x + attention(layer_norm(x))    # 3 kernels
x = x + ffn(layer_norm(x))          # 3 kernels

# 每个kernel都要读写HBM
# 总HBM流量 ~ 12x模型大小

# 融合: 2个大kernels
x = fused_attention_block(x)   # attention + norm + residual
x = fused_ffn_block(x)         # ffn + norm + residual

# HBM流量 ~ 4x模型大小
# 节省3倍带宽！✅
```

**Fusion的挑战**:
```
1. 寄存器压力
   - 更多中间值需要寄存器
   - 可能降低Occupancy

2. 代码复杂度
   - 融合的kernel更难写
   - 需要手动优化

3. 灵活性降低
   - 融合的kernel不通用
   - 每种组合需要单独写

权衡: 性能 vs 开发成本

解决方案:
- PyTorch: torch.compile (自动融合)
- JAX: XLA编译器
- Triton: 易写且高性能
```

- FlashAttention就是融合!
- QK^T + Softmax + PV 全在一个kernel
- 这也是为什么快的原因

### Q19: 什么是Occupancy？如何优化？

**引导思考**:
- SM可以同时运行多个warp
- 但是有限制...
- Occupancy衡量什么？

**Occupancy定义**:
```
Occupancy = 活跃warps / 最大warps

A100: 最大64 warps/SM

例子:
实际运行32 warps
→ Occupancy = 32/64 = 50%
```

**为什么重要？**:
```
高Occupancy → 更好的延迟隐藏
→ 内存访问时可以切换warp
→ GPU不闲置

低Occupancy → 延迟暴露
→ 等待内存时没有其他warp执行
→ GPU闲置 ⚠️
```

**限制因素**:
```python
def calculate_occupancy(
    threads_per_block: int,
    registers_per_thread: int,
    shared_mem_per_block: int
):
    # 1. Warp限制
    warps_per_block = threads_per_block // 32
    max_blocks_warp = 64 // warps_per_block
    
    # 2. 寄存器限制
    regs_per_block = threads_per_block * registers_per_thread
    max_blocks_reg = 65536 // regs_per_block
    
    # 3. Shared Memory限制
    max_blocks_smem = (164*1024) // shared_mem_per_block
    
    # 4. 物理限制 (A100: max 16 blocks/SM)
    max_blocks_physical = 16
    
    # 实际能跑的blocks
    actual_blocks = min(
        max_blocks_warp,
        max_blocks_reg,
        max_blocks_smem,
        max_blocks_physical
    )
    
    # Occupancy
    actual_warps = actual_blocks * warps_per_block
    occupancy = actual_warps / 64
    
    return occupancy, {
        'bottleneck': identify_bottleneck(),
        'actual_blocks': actual_blocks,
        'actual_warps': actual_warps
    }
```

**优化策略**:
```
1. 减少寄存器使用
   - 编译器选项: -maxrregcount=32
   - 代码优化: 减少局部变量
   
2. 减少Shared Memory使用
   - 只缓存必要数据
   - 使用更小的tile size

3. 调整Block Size
   - 256线程/block (8 warps) 通常较好
   - 太大: 资源瓶颈
   - 太小: 无法隐藏延迟

4. Profile和迭代
   - 使用Nsight Compute
   - 查看 "Occupancy" 指标
   - 识别瓶颈资源
```

**实际案例**:
```c

    float local[1000];                // 1000个寄存器！

}
```

### Q20: Warp Divergence如何影响性能？

**引导思考**:
- Warp内32个线程执行相同指令
- 如果有if-else分支呢？
- 性能会怎样？

**Warp Divergence的机制**:
```c
__global__ void divergent_kernel(int* data) {
    int x = data[threadIdx.x];
    
    if (x > 0) {          // 分支！
        // Path A: 一半线程走这里
        x = x * 2;
    } else {
        // Path B: 另一半线程走这里
        x = x + 1;
    }
}

执行过程:
1. 计算条件 (x > 0) for 所有32线程
2. Path A: 执行 x*2, Path B线程闲置 ⚠️
3. Path B: 执行 x+1, Path A线程闲置 ⚠️
4. 汇合

实际时间 = Time(Path A) + Time(Path B)
vs 理想 = max(Time(Path A), Time(Path B))

性能损失 ~ 50% (如果分支均匀)
```

**量化分析**:
```python
def divergence_cost(
    branch_probability: float,
    instructions_true: int,
    instructions_false: int
):
    # 无分支
    no_div_time = max(instructions_true, instructions_false)
    
    # 有分支（串行执行）
    with_div_time = instructions_true + instructions_false
    
    # 性能损失
    slowdown = with_div_time / no_div_time
    
    return slowdown

# 例子
slowdown = divergence_cost(
    branch_probability=0.5,
    instructions_true=10,
    instructions_false=10
)
# → slowdown = 2x ⚠️⚠️
```

**如何避免**:
```c
// 方法1: Predication (条件执行)
__global__ void no_divergence_v1(int* data) {
    int x = data[threadIdx.x];
    int mask = x > 0;
    
    // 全部线程都执行，但结果有条件地写入
    int result_a = x * 2;
    int result_b = x + 1;
    int result = mask ? result_a : result_b;
    
    data[threadIdx.x] = result;
}

// 方法2: 重新组织数据
// 将满足条件的data放一起
// 不同warp处理不同case
// → 每个warp内部无分支 ✅

// 方法3: 尽可能避免分支
// 用数学运算代替条件
int result = x * (x > 0) * 2 + x * (x <= 0) + (x <= 0);
```

**实际优化建议**:
```
1. Profile divergence
   - Nsight Compute: "Warp Divergence" 指标
   - 识别问题kernels

2. 优先级
   - 内层循环: 必须避免
   - 外层循环/初始化: 影响小

3. 权衡
   - 有时predication更慢（多余计算）
   - 需要实测

4. 特殊情况
   - Warp Vote Functions (__any, __all)
   - 有些分支是必要的
```

**连接实际应用**:
- Softmax kernel: 需要max reduction
  - 如何避免divergence？
- Sparse operations: 天然有divergence
  - 如何优化？

### Q21: Tensor Cores是什么？

**引导思考**:

**Tensor Cores基础**:
```
专用硬件单元，用于矩阵乘法
支持: FP16, BF16, TF32, INT8, INT4

每个Tensor Core (A100):
一个cycle内完成: 4×4×4矩阵乘法
= 128 FLOP/cycle (FP16)

vs 标准CUDA Core:
1-2 FLOP/cycle

加速: 64-128倍！✅✅✅
```

**数学操作**:
```python
# Tensor Core执行
D = A @ B + C

其中:
A: [M, K] (FP16)
B: [K, N] (FP16)
C: [M, N] (FP32)  # 累加器用FP32！
D: [M, N] (FP32)

关键:
- 输入: FP16 (低精度，快)
- 累加: FP32 (高精度，准确)
- 输出: FP32

这就是"混合精度"的硬件支持！
```

**如何使用**:
```c
// CUDA API
#include <mma.h>

__global__ void tensor_core_matmul() {
    // 声明fragments
    wmma::fragment<wmma::matrix_a, 16, 16, 16, half> a_frag;
    wmma::fragment<wmma::matrix_b, 16, 16, 16, half> b_frag;
    wmma::fragment<wmma::accumulator, 16, 16, 16, float> c_frag;
    
    // 加载
    wmma::load_matrix_sync(a_frag, A, lda);
    wmma::load_matrix_sync(b_frag, B, ldb);
    wmma::fill_fragment(c_frag, 0.0f);
    
    // 矩阵乘法 (使用Tensor Core!)
    wmma::mma_sync(c_frag, a_frag, b_frag, c_frag);
    
    // 存储
    wmma::store_matrix_sync(C, c_frag, ldc, wmma::mem_row_major);
}
```

### Q23: Async Copy如何加速？

**引导思考**:
- 内存拷贝和计算能同时进行吗？
- GPU有什么机制支持？
- 如何hide拷贝延迟？

**Async Copy机制**:
```c
// 同步拷贝 (旧方式)
__global__ void sync_copy_kernel() {
    __shared__ float smem[1024];
    
    // 1. 拷贝: HBM → Shared Memory
    for (int i = threadIdx.x; i < 1024; i += blockDim.x) {
        smem[i] = global_mem[i];
    }
    __syncthreads();  // 等待拷贝完成
    
    // 2. 计算
    compute(smem);
}
// 串行: Copy时间 + 计算时间

// 异步拷贝 (A100+, CUDA 11+)
__global__ void async_copy_kernel() {
    __shared__ float smem[1024];
    
    // 1. 发起异步拷贝
    __pipeline_memcpy_async(smem, global_mem, 1024 * sizeof(float));
    
    // 2. 立即开始计算其他数据
    compute_other_data();
    
    // 3. 等待拷贝完成
    __pipeline_wait_prior(0);
    
    // 4. 使用拷贝的数据
    compute(smem);
}
// 并行: max(Copy时间, 计算时间) ✅
```

**硬件支持**:
```
A100引入: Asynchronous Copy Engine

功能:
- 独立的DMA引擎
- 与SM并行工作
- 直接: HBM → Shared Memory
- 不占用SM资源！

pipeline深度:
- 可以同时进行多个异步拷贝
- Double/Triple buffering
```

**Double Buffering示例**:
```c
__global__ void double_buffer_kernel() {
    __shared__ float buffer[2][TILE_SIZE];
    
    int active = 0;
    
    // Prefetch第一个tile
    __pipeline_memcpy_async(
        buffer[active],
        &global_mem[0],
        TILE_SIZE * sizeof(float)
    );
    
    for (int tile = 1; tile < num_tiles; tile++) {
        // Prefetch下一个tile (到buffer[1-active])
        __pipeline_memcpy_async(
            buffer[1-active],
            &global_mem[tile * TILE_SIZE],
            TILE_SIZE * sizeof(float)
        );
        
        // 等待当前tile拷贝完成
        __pipeline_wait_prior(0);
        
        // 计算当前tile (同时下一个tile在拷贝!)
        compute(buffer[active]);
        
        // 切换buffer
        active = 1 - active;
    }
    
    // 最后一个tile
    __pipeline_wait_prior(0);
    compute(buffer[active]);
}

效果:
拷贝和计算完全overlap!
→ 隐藏内存延迟 ✅
```

**性能提升**:
```python
# 理论分析
copy_time = data_size / memory_bandwidth
compute_time = flops / compute_throughput

# 同步
total_time_sync = copy_time + compute_time

# 异步
total_time_async = max(copy_time, compute_time)

# 加速比
speedup = total_time_sync / total_time_async

# 例子: copy_time = 1ms, compute_time = 0.5ms
speedup = 1.5 / 1.0 = 1.5x ✅
```

**何时有效**:
```
有效场景:
- Memory-bound kernels
- Copy时间 > Compute时间
- 有足够Shared Memory做buffering

无效场景:
- Compute-bound kernels
- Compute时间 >> Copy时间
- Shared Memory不足

最适合: FlashAttention类算法!
```
