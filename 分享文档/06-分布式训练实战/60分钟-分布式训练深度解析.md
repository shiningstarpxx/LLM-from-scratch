```
              All-Reduce
              (梯度同步)
                    │
              统一更新参数
```

## 2.2 PyTorch DDP实现

```python
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP

def setup(rank, world_size):

    # 设置当前GPU

    # 创建模型并包装
    model = MyModel().to(rank)
    model = DDP(model, device_ids=[rank])

    # 创建分布式sampler
    sampler = DistributedSampler(dataset, num_replicas=world_size, rank=rank)
    dataloader = DataLoader(dataset, sampler=sampler, batch_size=local_batch)

    # 训练循环
    for epoch in range(epochs):
        sampler.set_epoch(epoch)  # 保证每个epoch数据不同

            loss.backward()  # DDP自动同步梯度
```

## 2.3 All-Reduce详解

```
Ring All-Reduce算法:

假设4个GPU，每个有参数 [a, b, c, d]

Step 1-3: Reduce-Scatter
每个GPU把自己的1/4发给下一个GPU，同时累加收到的

GPU0: [a0+a3, b0, c0, d0] → [a0+a3, b0+b3, c0, d0] → ...
GPU1: [a1, b1+b0, c1, d1] → ...
GPU2: [a2, b2, c2+c1, d2] → ...
GPU3: [a3, b3, c3, d3+d2] → ...

最终: 每个GPU有1/4的完整结果

Step 4-6: All-Gather
把完整的1/4广播给所有GPU

结果: 每个GPU都有完整的全局和
通信量: 2 × (N-1)/N × P ≈ 2P (与GPU数量N无关!)
```

## 2.4 DDP通信优化

```python
# DDP的关键优化: Gradient Bucketing

class OptimizedDDP:
    """
    DDP不是等所有梯度算完再通信
    而是分桶异步通信
    """
    def __init__(self, model, bucket_size_mb=25):
        self.model = model
        self.bucket_size = bucket_size_mb * 1024 * 1024

        # 按逆序分桶 (因为backward从后往前算)
        self.buckets = self._create_buckets()

    def backward(self, loss):
        loss.backward()

        # 每个桶满了就开始All-Reduce
        # 与后续层的backward重叠
        for bucket in self.buckets:
            if bucket.is_ready():
                async_all_reduce(bucket)

# 效果: 通信和计算重叠，减少总时间
```

# Part 3: ZeRO优化原理

---

## 3.1 ZeRO三阶段

```
ZeRO (Zero Redundancy Optimizer)

核心思想: 把冗余数据分片到各GPU

┌─────────────────────────────────────────────┐
│ Stage   分片内容                  通信增加   │
├─────────────────────────────────────────────┤
│ ZeRO-1  优化器状态 (m, v)        无         │
│ ZeRO-2  + 梯度                   无         │
│ ZeRO-3  + 模型参数               +50%       │
└─────────────────────────────────────────────┘
```

---

## 3.2 ZeRO-1: 分片优化器状态

```
标准数据并行 (每卡):
- 模型: 14GB
- 梯度: 14GB
- Adam: 56GB  ← 每卡都有完整副本
总计: 84GB

ZeRO-1 (8卡):
- 模型: 14GB
- 梯度: 14GB
- Adam: 56GB / 8 = 7GB  ← 分片!
总计: 35GB

工作流程:
1. 所有卡做前向、反向
2. All-Reduce梯度
3. 每卡只更新自己负责的1/8参数
4. All-Gather更新后的参数
```

---

## 3.3 ZeRO-2: 分片梯度

```
ZeRO-2 (8卡):
- 模型: 14GB
- 梯度: 14GB / 8 = 1.75GB  ← 也分片!
- Adam: 56GB / 8 = 7GB
总计: 22.75GB

关键变化:
- 使用Reduce-Scatter代替All-Reduce
- 每卡只保留自己需要的梯度分片
- 内存从84GB降到23GB

Reduce-Scatter vs All-Reduce:
- All-Reduce: 每卡都有完整结果
- Reduce-Scatter: 每卡有1/N结果
- 通信量相同!
```

---

## 3.4 ZeRO-3: 分片参数

```
ZeRO-3 (8卡):
- 模型: 14GB / 8 = 1.75GB  ← 参数也分片!
- 梯度: 14GB / 8 = 1.75GB
- Adam: 56GB / 8 = 7GB
总计: 10.5GB

代价: 需要额外通信

前向传播:
for layer in layers:
    params = All-Gather(layer.params_shard)  # 收集完整参数
    output = layer(input, params)
    Release(params_not_mine)  # 释放非本分片参数

反向传播:
for layer in reversed(layers):
    params = All-Gather(layer.params_shard)  # 再次收集
    grad = backward(layer, params)
    Reduce-Scatter(grad)  # 只保留本分片梯度
```

---

## 3.5 ZeRO通信分析

```
假设: N卡, P参数量

数据并行 (All-Reduce):
通信量 = 2P (Reduce-Scatter + All-Gather)

ZeRO-1:
通信量 = 2P (同上)

ZeRO-2:
通信量 = 2P (同上)

ZeRO-3:
通信量 = 3P (额外的参数All-Gather)
- 前向: All-Gather参数 = P
- 反向: All-Gather参数 = P
- 反向: Reduce-Scatter梯度 = P
总计: 3P, 增加50%
```

# Part 4: 模型并行技术

---

## 4.1 为什么需要模型并行?

```
场景: ZeRO-3 + 8卡仍然不够

例如: 175B模型
- ZeRO-3每卡: 175B / 8 × 16bytes ≈ 350GB
- 仍远超80GB

解决: 把模型切分到多卡
- 张量并行 (TP): 切分层内
- 流水线并行 (PP): 切分层间
```

---

## 4.2 张量并行: 列切分

```
切分Linear层: Y = XW + b

列切分 (Column Parallel):
W = [W1 | W2]  按列切分

GPU 0: Y1 = X @ W1
GPU 1: Y2 = X @ W2
结果: Y = [Y1 | Y2]  (无需通信!)

后续如果需要完整Y:
Y = All-Gather([Y1, Y2])
```

---

## 4.3 张量并行: 行切分

```
行切分 (Row Parallel):
W = [W1]
    [W2]

X = [X1 | X2]  (输入也要切分)

GPU 0: Y1 = X1 @ W1
GPU 1: Y2 = X2 @ W2
结果: Y = Y1 + Y2  (All-Reduce)
```

---

## 4.4 Transformer的张量并行

```
MLP层切分策略:

     X (完整)
     │
     ├───────────────────┐
     │                   │
  GPU 0               GPU 1
 W1 列切分            W1 列切分
     │                   │
   GELU               GELU
     │                   │
 W2 行切分            W2 行切分
     │                   │
     └─────────┬─────────┘
           All-Reduce
               │
             Y (完整)

通信: 每个MLP层1次All-Reduce
```

## 4.5 Attention的张量并行

```
Multi-Head Attention并行:

假设8个头，2卡张量并行

GPU 0: Head 0-3
GPU 1: Head 4-7

Q, K, V各自列切分
每卡独立计算自己的头
输出投影行切分
最后All-Reduce

通信: 每个Attention层1次All-Reduce
```

```python
        # 每卡只存1/tp_size列

            torch.randn(in_features, out_features // tp_size)
```

## 4.7 流水线并行

```
按层切分模型:

GPU 0: Layer 0-7
GPU 1: Layer 8-15
GPU 2: Layer 16-23
GPU 3: Layer 24-31

数据流:
batch → GPU0 → GPU1 → GPU2 → GPU3 → loss
                                      │
batch ← GPU0 ← GPU1 ← GPU2 ← GPU3 ←───┘

问题: Pipeline Bubble
- GPU0算完layer0-7后必须等
- GPU3要等很久才能开始
- 效率低!
```

---

## 4.8 Pipeline Bubble优化

```
解决: Micro-batching

原始: 1个大batch
改进: 切成多个micro-batch

        time →
GPU 0: [M1][M2][M3][M4][B4][B3][B2][B1]
GPU 1:    [M1][M2][M3][M4][B4][B3][B2][B1]
GPU 2:       [M1][M2][M3][M4][B4][B3][B2][B1]
GPU 3:          [M1][M2][M3][M4][B4][B3][B2][B1]

M = micro-batch前向
B = micro-batch反向

Bubble比例 = (p-1) / (m + p - 1)
p = pipeline stages
m = micro-batches

m=4, p=4: bubble = 3/7 = 43%
m=8, p=4: bubble = 3/11 = 27%
```

---

## 4.9 Pipeline调度策略

```
GPipe Schedule:
- 先做完所有前向
- 再做所有反向
- 简单但bubble大

1F1B Schedule (One Forward One Backward):
- 前向反向交替
- 减少峰值内存
- DeepSpeed/Megatron默认

Interleaved Schedule:
- 每卡负责多组非连续层
- 进一步减少bubble
- 更复杂的实现
```

# Part 5: 3D并行与实践

---

## 5.1 3D并行架构

```
大模型标配: DP × TP × PP

例如: 64卡训练175B

配置:
- TP = 8 (一个节点内，需要高带宽NVLink)
- PP = 4 (跨节点)
- DP = 64 / 8 / 4 = 2

每个维度解决不同问题:
- TP: 切分单层，需要高带宽
- PP: 切分层，可跨节点
- DP: 扩展batch，通信最少
```

---

## 5.2 并行度选择策略

```
原则:

1. TP优先在节点内
   - 需要NVLink高带宽 (600 GB/s)
   - 跨节点TP效率很低

2. PP处理深度
   - 层数/PP要能整除
   - 适度PP减少TP通信

3. DP扩展规模
   - 通信量最少
   - 尽可能大

配置示例:

| 模型 | 卡数 | TP | PP | DP |
|------|------|----|----|-----|
| 7B | 8 | 1 | 1 | 8 |
| 30B | 16 | 4 | 2 | 2 |
| 70B | 64 | 8 | 4 | 2 |
| 175B | 128 | 8 | 8 | 2 |
```

```
┌──────────────────────────────────────────┐
│ 模型大小        推荐策略                  │
├──────────────────────────────────────────┤
│ < 10B          DDP                       │
│ 10B - 30B      ZeRO-2 或 ZeRO-3          │
│ 30B - 100B     ZeRO-3 + TP               │
│ > 100B         3D并行 (DP + TP + PP)      │
└──────────────────────────────────────────┘

硬件考虑:
- 单节点: 优先ZeRO
- 多节点 + NVLink: 可用TP
- 跨节点: PP更合适
```

---

## 6.2 核心概念回顾

| 策略 | 核心思想 | 通信 | 代价 |
|------|----------|------|------|
| DDP | 模型复制 | All-Reduce | 内存冗余 |
| ZeRO | 状态分片 | 按stage | 实现复杂 |
| TP | 切分矩阵 | 每层通信 | 需高带宽 |
| PP | 切分层 | 边界通信 | Bubble |

---

## 6.3 关键数字

```
通信带宽需求:

DDP/ZeRO:
- 梯度同步 = 2 × 模型大小
- 7B模型 ≈ 28GB/step

TP (每层):
- 2-4次 All-Reduce
- 激活大小相关

PP:
- 激活传递
- 相对最少

推荐带宽:
- TP: NVLink 600 GB/s
- PP/DP: InfiniBand 200 Gbps
```

## 6.4 常见误区

| 误区 | 正确理解 |
|------|----------|
| 更多卡总是更快 | 通信可能成瓶颈 |
| ZeRO-3最好 | 通信开销大，需权衡 |
| 只用一种并行 | 大模型需要组合 |
| TP可以跨节点 | 跨节点效率很低 |
| Pipeline简单 | Bubble和内存管理复杂 |

## Q&A

### Q1: ZeRO-2和ZeRO-3怎么选?
**A**: ZeRO-2内存够用就用ZeRO-2，因为通信少。ZeRO-3通信增加50%，只在内存实在不够时用。

### Q2: FSDP和DeepSpeed哪个好?
**A**: 功能类似。FSDP是PyTorch原生，集成好。DeepSpeed功能更丰富(如Offload)，优化更激进。

### Q3: 为什么TP需要高带宽?
**A**: TP在每层都需要通信，延迟直接影响训练速度。NVLink比网络快10-100倍。

### Q4: 如何确定最优并行配置?
**A**: 需要实验。一般原则: TP=节点内GPU数, PP使层可整除, 剩余给DP。
